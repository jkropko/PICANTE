# --- The CSV endpoint was tried first, and failed ------------------------
#
# The stronger route would have been to archive the export itself — one save
# covering all 890 grants, as ACT's raw members.yml was archived at its pinned
# commit instead of the rendered page. A Wayback save of the CSV endpoint was
# attempted on the capture date and FAILED.
#
# The reason is structural rather than transient: the "Download as CSV file"
# control carries an empty href and a csv title attribute, so the file is
# assembled client-side or served as an attachment. Either way there is no
# stable URL for the archive to fetch. Re-attempting will not help.
#
# Recorded because the failure explains why a weaker route was used. The
# attempt is part of the method, not an omission from it.

# --- What these four snapshots do and do not cover -----------------------
#
# COVER: the frame's size (89 pages), its recency, its midpoint, and its depth
# back to the oldest grants. Each of the four supports a specific claim made in
# notes.txt rather than sampling at random.
#
# DO NOT COVER: the membership. 40 of 890 grants are archived. Nobody was ever
# going to reconstruct this frame from archived HTML — the downloaded CSV,
# hashed in capture_log.json and deposited on OSF, is the record.
#
# THE LIMITATION, STATED PLAINLY. This is the fastest-moving frame in the
# register: McGovern updates the grants database WEEKLY. A re-fetch a month
# from now returns a materially different set — more so than Fast Forward,
# which grows once per cohort. So the archive is doing more work here than
# anywhere else in the register, and four pages of it is thin. A reader who
# doubts the captured membership can verify the frame's shape and span from a
# third party, but not its contents.
#
# Archiving all 89 would close that gap at the cost of 89 manual saves against
# a rate limit. It was judged disproportionate. Every tenth page (ten saves)
# would be the obvious middle course if this later matters.
